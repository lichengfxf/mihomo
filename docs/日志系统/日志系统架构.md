# 日志系统架构

本文说明 mihomo 当前日志系统的实现方式，覆盖日志入口、级别控制、控制台输出、事件分发以及外部控制器 `/logs` 的消费链路。

## 1. 总体结论

当前日志系统不是一个“可插拔多后端日志框架”，而是一个较薄的自定义封装：

- 对内提供统一的 `log.Infoln`、`log.Warnln`、`log.Errorln`、`log.Debugln`
- 对外默认只写到标准输出 `stdout`
- 同时把日志作为事件投递到内存中的发布订阅通道
- Web 控制器通过订阅该事件流，把日志实时推送给 UI 或其他客户端

也就是说，它本质上是：

`业务代码 -> 自定义 log 包 -> 事件广播 + logrus 控制台输出 -> /logs 实时消费`

当前实现没有独立的日志落盘模块，也没有按文件滚动、异步批量刷盘、结构化索引存储这类能力。

## 3. 日志数据结构

内部日志事件结构非常简单：

```go
type Event struct {
	LogLevel LogLevel
	Payload  string
}
```

特点：

- `LogLevel` 表示日志级别
- `Payload` 是已经格式化完成的纯文本消息
- 不带时间戳字段
- 不带模块名、trace id、字段集合等结构化上下文

时间戳目前不是由 `Event` 保存，而是在输出阶段临时生成：

- 输出到控制台时，由 logrus formatter 负责
- 输出到 `/logs?format=structured` 时，由接口层即时生成

这意味着：

- 同一条日志在不同消费端看到的时间可能不是同一个“事件生成时间”
- 当前实现更接近“文本日志广播”，不是严格意义上的结构化日志事件模型

## 4. 日志初始化

`log/log.go` 的 `init()` 会在进程启动时初始化底层输出：

- `log.SetOutput(os.Stdout)`：输出到标准输出
- `log.SetLevel(log.DebugLevel)`：底层 logrus 允许 debug 及以上
- `log.SetFormatter(&log.TextFormatter{...})`：使用文本格式并带完整时间戳

这里有一个关键点：

底层 logrus 级别固定设成了 `DebugLevel`，真正的日志过滤不依赖 logrus，而是依赖 mihomo 自己维护的全局变量：

```go
var level = INFO
```

也就是说：

- logrus 负责“怎么打印”
- mihomo 自定义 `level` 负责“哪些日志允许打印和分发”

## 5. 日志写入链路

### 5.1 业务调用入口

项目内大多数模块直接调用：

- `log.Infoln`
- `log.Warnln`
- `log.Errorln`
- `log.Debugln`

例如监听器、配置加载、TUN、外部控制器等模块都走这条路径。

### 5.2 生成事件

每个日志函数都会先调用 `newLog`：

```go
func newLog(logLevel LogLevel, format string, v ...any) Event {
	return Event{
		LogLevel: logLevel,
		Payload:  fmt.Sprintf(format, v...),
	}
}
```

也就是说，日志在进入系统时就已经被格式化成完整字符串，不再保留参数化模板。

### 5.3 投递到事件通道

日志函数会执行：

```go
logCh <- event
```

这里的 `logCh` 是一个无缓冲 channel：

```go
var logCh = make(chan Event)
```

这意味着日志写入方会和后面的 observable 处理链发生同步交接。只要接收方 goroutine 正常运行，通常不会有问题；但从架构上说，它不是完全无阻塞的异步日志。

### 5.4 同步打印到控制台

在事件投递之后，日志函数会立刻调用 `print(event)`。

`print` 的逻辑是：

1. 用全局 `level` 过滤低级别日志
2. 按级别调用 logrus 的 `Infoln/Warnln/Errorln/Debugln`

所以一次日志调用实际上会触发两件事：

- 进入事件总线，供订阅者消费
- 输出到 stdout，供终端、systemd、docker logs 等采集


对应代码：

### 6.3 运行时动态修改

外部控制器 `PATCH /configs` 支持动态更新 `log-level`，最终同样调用：

```go

```

对应代码：

这说明日志级别不是启动时写死的，可以在运行中调整。

### 6.4 过滤语义

当前级别顺序是：

- `DEBUG = 0`
- `INFO = 1`
- `WARNING = 2`
- `ERROR = 3`
- `SILENT = 4`

过滤条件是：

```go
if data.LogLevel < level {
	return
}
```

因此：

- `level = info` 时，输出 `info/warning/error`
- `level = warning` 时，输出 `warning/error`
- `level = error` 时，只输出 `error`
- `level = silent` 时，控制台和 `/logs` 都不会看到任何日志事件

注意：日志事件虽然先写进 `logCh`，但 `/logs` 消费端也会再次按级别过滤，因此 `silent` 依然会让对外日志流为空。

## 7. 事件广播机制

### 7.1 广播模型

`observable.Observable` 内部维护一个订阅者 map：

```go
listener map[Subscription[T]]*Subscriber[T]
```

后台 goroutine 从 `iterable` 读取数据后，会向所有订阅者逐个 `Emit(item)`。

因此它是一个典型的“单生产源，多订阅复制”的广播模型，而不是多个消费者竞争消费同一条日志。

### 7.2 订阅与退订

日志包对外暴露：

- `log.Subscribe()`
- `log.UnSubscribe(sub)`

任何模块都可以实时订阅日志流，但当前仓库里最主要的订阅方是 `/logs` 接口。

### 7.3 每个订阅者的缓冲

`Subscriber` 内部缓冲区大小为：

```go
make(chan T, 200)
```

也就是说，每个订阅者最多可积压 200 条日志，超过之后发送端会阻塞在 `sub.Emit(item)`。

从实现上看，`observable.process()` 是串行地向所有订阅者发消息，所以如果某个订阅者长时间不消费，可能拖慢整个广播链路。

## 8. `/logs` 接口如何消费日志

### 8.1 接口位置

路由注册在：

- [hub/route/server.go](/vm/project/github/clash-meta/mihomo/hub/route/server.go:102)

对应处理函数 `getLogs` 在：

- [hub/route/server.go](/vm/project/github/clash-meta/mihomo/hub/route/server.go:480)

### 8.2 支持的输入参数

`/logs` 会读取两个关键 query 参数：

- `level`
- `format`

其中：

- `level` 用于指定最小日志级别
- `format=structured` 时返回结构化格式

如果 `level` 非法，会直接返回 `400 Bad Request`。

### 8.3 连接方式

`/logs` 同时支持两种传输方式：

- 普通 HTTP 持续写出
- `Upgrade: websocket` 的 WebSocket 推送

如果不是 WebSocket：

- 响应头设为 `Content-Type: application/json`
- 每条日志都会单独编码成一段 JSON 并立刻 `Flush`

### 8.4 订阅方式

`getLogs` 会调用：

```go
sub := log.Subscribe()
defer log.UnSubscribe(sub)
```

然后再起一个 goroutine，把订阅到的日志转发到本地缓冲通道：

```go
ch := make(chan log.Event, 1024)
```

这里有两个额外设计点：

1. `ch` 比 subscriber 自身缓冲更大，减少 HTTP 写出端的瞬时压力
2. 转发时使用 `select { case ch <- logM: default: }`

第二点意味着：

- 如果 `/logs` 客户端消费过慢
- 本地 1024 缓冲已满

那么新日志会被直接丢弃，而不是阻塞整个日志系统。

这也是 `/logs` 接口和内部总线之间的隔离层。

### 8.5 输出格式

非 `structured` 模式下返回：

```json
{"type":"info","payload":"..."}
```

`structured` 模式下返回：

```json
{
  "time": "15:04:05",
  "level": "info",
  "message": "...",
  "fields": []
}
```

这里的 `warning` 会被转换为 `warn`，更贴近部分前端或日志查看器的习惯。

## 11. 当前实现的优点

- 结构简单，调用成本低，业务模块接入统一
- 控制台输出和 UI 日志流复用同一份事件，不会出现“两套日志内容不一致”
- 运行时可动态调整 `log-level`
- 对 `sing` 生态的日志适配已经打通，减少外围组件割裂
- `/logs` 接口对慢客户端做了 1024 队列和丢弃保护，避免直接拖垮外部控制器写出

## 12. 当前实现的局限

### 12.1 没有持久化落盘

当前默认只输出到 `stdout`，没有内建：

- 日志文件
- 按大小或日期滚动
- 历史日志保留策略

如果需要持久化，通常依赖外部运行环境采集：

- systemd journal
- Docker/Kubernetes 日志
- shell 重定向

### 12.2 事件模型偏文本

`Event` 只有 `LogLevel + Payload`，缺少：

- 事件时间
- 模块名
- 连接 ID
- 结构化字段
- trace/span 上下文

因此对自动分析、聚合检索、不同行为维度统计并不友好。

### 12.3 内部总线存在背压风险

虽然 `/logs` 对外写出做了丢弃保护，但 `observable` 内部仍是串行广播：

- `logCh` 无缓冲
- 每个 subscriber 缓冲只有 200
- 某个订阅者若卡住，可能拖慢广播 goroutine

当前场景下问题通常不大，因为主要订阅方集中在外部控制器，且控制器内部已经做了二级缓冲；但从架构上说，这不是一个高吞吐、强隔离的日志管道。

### 12.4 时间戳不是事件固有属性

控制台时间来自 logrus formatter，`structured` 输出时间来自 `/logs` 写出时刻。严格来说，这两者都不是“日志产生时间”的稳定表达。

## 13. 当前日志系统的真实架构图

```text
业务模块
  ├─ listener / tunnel / config / hub / adapter ...
  │
  └─ 调用 log.Infoln / Warnln / Errorln / Debugln
            │
            ├─ newLog() 生成 Event{LogLevel, Payload}
            │
            ├─ 写入 logCh
            │      │
            │      └─ observable.process() 广播给所有订阅者
            │               │
            │               └─ /logs 订阅者
            │                      ├─ 本地缓冲 chan(1024)
            │                      ├─ 级别过滤
            │                      └─ HTTP Flush / WebSocket 推送
            │
            └─ print()
                   ├─ 按全局 level 过滤
                   └─ logrus 输出到 stdout
```

## 14. 一句话总结

当前 mihomo 的日志系统是“自定义轻量日志门面 + 内存事件广播 + stdout 输出 + `/logs` 实时推送”的组合实现，重点在统一接入和实时观察，不在本地持久化与复杂结构化处理。
