# 日志系统架构

本文说明 mihomo 当前日志系统的实现方式，覆盖日志入口、级别控制、控制台输出、文件输出、事件分发以及外部控制器 `/logs` 的消费链路。

## 1. 总体结论

当前日志系统仍然是一个较薄的自定义封装，但已经具备三条并行输出链路：

- 对内提供统一的 `log.Infoln`、`log.Warnln`、`log.Errorln`、`log.Debugln`
- 对外默认写到标准输出 `stdout`
- 同时支持写入滚动日志文件
- 同时把日志作为事件投递到内存中的发布订阅通道
- Web 控制器通过订阅该事件流，把日志实时推送给 UI 或其他客户端

当前主链路可以概括为：

`业务代码 -> 自定义 log 包 -> stdout + rotating file + /logs 实时消费`

## 3. 日志数据结构

内部日志事件结构仍然很简单：

```go
type Event struct {
	LogLevel LogLevel
	Payload  string
}
```

特点：

- `LogLevel` 表示日志级别
- `Payload` 是已经格式化完成的纯文本消息
- 不带时间戳字段
- 不带模块名、trace id、字段集合等结构化上下文

时间戳目前不是由 `Event` 保存，而是在输出阶段生成：

- 输出到控制台时，由 logrus formatter 负责
- 输出到文件时，由 `writeFile` 在写盘时生成 RFC3339Nano 时间
- 输出到 `/logs?format=structured` 时，由接口层即时生成

这意味着不同消费端看到的时间并不一定完全相同，`Event` 仍然更接近“文本日志广播”模型，而不是严格意义上的结构化事件模型。

## 4. 日志初始化

`log/log.go` 的 `init()` 会在进程启动时初始化底层控制台输出：

- `log.SetOutput(os.Stdout)`：输出到标准输出
- `log.SetLevel(log.DebugLevel)`：底层 logrus 允许 debug 及以上
- `log.SetFormatter(&log.TextFormatter{...})`：使用文本格式并带完整时间戳

真正的日志过滤不依赖 logrus，而是依赖 mihomo 自己维护的全局变量：

```go
var level = INFO
```

也就是说：

- logrus 负责“怎么打印控制台日志”
- mihomo 自定义 `level` 负责“哪些日志允许进入输出后端”

## 5. 日志写入链路

### 5.1 业务调用入口

项目内大多数模块直接调用：

- `log.Infoln`
- `log.Warnln`
- `log.Errorln`
- `log.Debugln`

### 5.2 生成事件

每个日志函数都会先调用 `newLog` 生成 `Event`，日志在进入系统时就已经被格式化成完整字符串，不再保留参数化模板。

### 5.3 投递到事件通道

日志函数会执行：

```go
logCh <- event
```

这里的 `logCh` 是无缓冲 channel，因此日志调用方会与后面的 `observable` 处理链同步交接。

### 5.4 统一分发

在事件投递之后，日志函数会立刻调用：

```go
dispatch(event)
```

`dispatch` 的逻辑是：

1. 用全局 `level` 过滤低级别日志
2. 调用 `writeConsole(event)`
3. 调用 `writeFile(event)`

因此一次日志调用实际上会触发三件事：

- 进入事件总线，供订阅者消费
- 输出到 stdout，供终端、systemd、docker logs 等采集
- 输出到本地滚动日志文件

## 6. 文件日志输出

### 6.1 配置字段

当前支持以下顶层配置：

```yaml
log-level: info
log-file: /var/log/sdc-mihomo/mihomo.log
log-file-format: text
log-file-append: true
log-file-max-size: 20
log-file-max-backups: 5
log-file-max-age: 7
log-file-compress: true
```

其中：

- 未配置 `log-file` 时，默认使用 `/var/log/sdc-mihomo/mihomo.log`
- 显式把 `log-file` 设为空字符串时，关闭文件输出
- 第一版仅支持 `log-file-format: text`

### 6.2 writer 生命周期

文件 writer 生命周期由 `log` 包统一管理：

1. `executor.ApplyConfig` 根据配置调用 `log.ApplyFileConfig`
2. `ApplyFileConfig` 先构造新 writer
3. 构造成功后替换当前 writer
4. 再关闭旧 writer

如果新 writer 构造失败：

- 保持旧 writer 不变
- 直接向 `stderr` 输出内部错误
- 不影响主业务和控制台输出

### 6.3 输出格式

文件日志固定为单行文本，例如：

```text
2026-05-11T14:32:15.123456789+08:00 [info] RESTful API listening at: 127.0.0.1:9090
```

格式字段包括：

- RFC3339Nano 时间戳
- 日志级别
- `Event.Payload`

### 6.4 滚动实现

当前通过 `gopkg.in/natefinch/lumberjack.v2` 实现按大小滚动，并支持：

- `log-file-max-size`
- `log-file-max-backups`
- `log-file-max-age`
- `log-file-compress`

### 6.5 错误处理

文件日志的内部错误不会调用上层 `log.Errorln`，而是直接写 `stderr`，避免递归。

同时带有限频和恢复提示：

- 同类错误在冷却窗口内会被合并
- 恢复后会补一条 recovered 提示

对应代码：

- [hub/route/configs.go](/vm/project/github/clash-meta/mihomo/hub/route/configs.go:1)

### 7.4 过滤语义

文件日志与控制台日志共用同一套级别过滤：

- `debug`：输出全部
- `info`：输出 `info/warning/error`
- `warning`：输出 `warning/error`
- `error`：只输出 `error`
- `silent`：控制台和文件都不输出

注意：日志事件依然会先写进 `logCh`，`/logs` 消费端再按请求级别过滤，因此 `silent` 时 `/logs` 对外也不会看到任何日志。

## 8. 事件广播机制

`observable.Observable` 内部维护订阅者 map，并由后台 goroutine 从 `logCh` 读取数据后向所有订阅者逐个广播。

这仍然是“单生产源，多订阅复制”的广播模型，而不是多个消费者竞争消费同一条日志。

当前仓库里最主要的订阅方仍是 `/logs` 接口。

## 9. `/logs` 接口如何消费日志

### 9.1 接口位置

路由注册在：

- [hub/route/server.go](/vm/project/github/clash-meta/mihomo/hub/route/server.go:102)

对应处理函数 `getLogs` 在：

- [hub/route/server.go](/vm/project/github/clash-meta/mihomo/hub/route/server.go:480)

### 9.2 支持的输入参数

`/logs` 会读取两个关键 query 参数：

- `level`
- `format`

### 9.3 连接方式

`/logs` 同时支持：

- 普通 HTTP 持续写出
- WebSocket 推送

### 9.4 慢客户端保护

`getLogs` 会先订阅日志，再通过本地 `chan(1024)` 转发到响应写出端；如果缓冲已满，新日志会被直接丢弃，而不是阻塞整个日志系统。

这也是 `/logs` 接口和内部总线之间的隔离层。

## 11. 当前实现的优点

- 结构简单，业务模块接入统一
- 控制台、文件和 `/logs` 复用同一份 `Event`
- 支持运行时修改 `log-level`
- 支持运行时切换日志文件路径和滚动参数
- 文件写入失败不会拖垮主业务
- `/logs` 对慢客户端做了额外缓冲和丢弃保护

## 12. 当前实现的局限

### 12.1 `Event` 仍偏文本

`Event` 只有 `LogLevel + Payload`，缺少：

- 事件时间
- 模块名
- 连接 ID
- 结构化字段

### 12.2 内部总线仍有背压风险

虽然 `/logs` 对外写出做了丢弃保护，但 `observable` 内部仍是串行广播：

- `logCh` 无缓冲
- 每个 subscriber 缓冲只有 200
- 某个订阅者若卡住，可能拖慢广播 goroutine

### 12.3 控制台时间、文件时间、`/logs structured` 时间来源不同

当前时间戳仍不是 `Event` 的固有字段，因此不同消费端看到的时间只保证“接近”，不保证完全一致。

## 13. 当前日志系统架构图

```text
业务模块
  └─ 调用 log.Infoln / Warnln / Errorln / Debugln
            │
            ├─ newLog() 生成 Event{LogLevel, Payload}
            │
            ├─ 写入 logCh
            │      │
            │      └─ observable.process() 广播给所有订阅者
            │               │
            │               └─ /logs 订阅者
            │                      ├─ 本地缓冲 chan(1024)
            │                      ├─ 级别过滤
            │                      └─ HTTP Flush / WebSocket 推送
            │
            └─ dispatch()
                   ├─ 按全局 level 过滤
                   ├─ writeConsole() -> logrus -> stdout
                   └─ writeFile() -> rotating file
```

## 14. 一句话总结

当前 mihomo 的日志系统是“自定义轻量日志门面 + stdout + rotating file + 内存事件广播 + `/logs` 实时推送”的组合实现，重点仍然是统一接入和实时观察，同时已经具备本地持久化能力。
