# 新增功能：输出日志到文件（正式设计）

## 1. 目标

为 mihomo 增加“日志输出到文件”能力，满足以下目标：

- 保持现有业务日志调用方式不变
- 文件日志与控制台日志共用同一条主链路
- 文件日志支持运行期配置重载
- 文件日志支持自动滚动，避免单文件无限增长
- 文件写入失败不影响代理主业务

本设计为定稿方案，不再保留备选路线。

## 2. 设计结论

日志文件输出将作为 `log` 包中的新输出后端实现，与现有控制台输出并列存在。

日志主链路定为：

`业务代码 -> log.Event -> 统一分发 -> stdout + file -> /logs 订阅消费`

具体约束如下：

- 业务模块继续只调用 `log.Infoln`、`log.Warnln`、`log.Errorln`、`log.Debugln`
- 文件输出不通过 `Subscribe()` 订阅实现
- 第一版采用同步串行写文件
- 第一版文件格式采用单行文本
- 第一版即内建日志滚动，并使用成熟库实现
- 配置先采用轻量顶层字段
- 支持配置 reload 后切换日志文件

## 3. 现状与改造边界

当前日志系统核心实现位于：

- [log/log.go](/vm/project/github/clash-meta/mihomo/log/log.go:1)
- [log/level.go](/vm/project/github/clash-meta/mihomo/log/level.go:1)
- [common/observable/observable.go](/vm/project/github/clash-meta/mihomo/common/observable/observable.go:1)
- [hub/route/server.go](/vm/project/github/clash-meta/mihomo/hub/route/server.go:480)

当前行为是：

1. 业务代码调用 `log.*ln`
2. 生成 `Event`
3. 写入 `logCh`
4. 同步打印到 `stdout`
5. `/logs` 通过订阅事件流实时消费

本次改造不改变：

- `Event` 事件模型
- `/logs` 的订阅模式
- `log-level` 的语义
- 业务层日志调用方式

本次改造只增加：

- 文件输出后端
- 文件日志配置
- 文件 writer 生命周期管理
- 滚动能力

## 4. 架构设计

### 4.1 总体结构

在 `log` 包内部新增统一输出分发层，把当前 `print(event)` 重构为更清晰的输出流程。

目标结构：

```text
log.Infoln / Warnln / Errorln / Debugln
  -> newLog(...)
  -> logCh <- event
  -> dispatch(event)
       -> writeConsole(event)
       -> writeFile(event)
```

其中：

- `writeConsole(event)` 负责现有 `stdout` 输出
- `writeFile(event)` 负责文件落盘
- `logCh` 和 `observable` 保持原样，继续为 `/logs` 提供事件流

### 4.2 为什么文件输出不走订阅模式

文件输出是日志系统主后端的一部分，不是外围消费者。

当前 `observable` 机制适合 UI 或调试类实时消费，但不适合作为可靠落盘主通道，原因如下：

- 订阅者是广播模型中的普通消费者，职责层级不对
- 当前内部广播存在背压风险
- 文件写入应与控制台输出共享同一套主过滤和生命周期管理

因此文件输出必须直接挂在 `log` 包主分发链路中。

## 5. 输出模型

### 5.1 同步串行写

第一版采用同步串行写文件，不引入异步落盘 goroutine。

每条日志执行顺序固定为：

1. 生成 `Event`
2. 投递到 `logCh`
3. 执行统一分发
4. 按级别输出到控制台
5. 按级别输出到文件

这样设计的原因：

- 实现简单
- 语义稳定
- 不需要处理异步队列积压、退出 flush、丢日志等问题
- 与当前日志系统整体复杂度一致

### 5.2 顺序保证

文件 writer 在进程内保持单实例，并以串行追加方式写入日志文件，保证单进程内日志顺序与主调用顺序一致。

## 6. 文件输出格式

第一版文件格式固定为单行文本：

```text
2026-05-11T14:32:15.123456+08:00 [info] RESTful API listening at: 127.0.0.1:9090
```

格式字段定义：

- 时间：RFC3339 风格高精度时间戳
- 级别：`[debug]`、`[info]`、`[warning]`、`[error]`
- 消息：`Event.Payload`

选择文本格式的原因：

- 便于人工直接查看
- 与现有控制台风格接近
- 对路由器、网关、服务器场景更实用
- 对命令行工具链更友好

第一版不提供 JSON Lines 文件格式。

## 7. 日志级别语义

文件日志与控制台日志共用同一套 `log-level` 过滤逻辑，不增加单独的文件日志级别。

即：

- `debug`：输出全部
- `info`：输出 `info/warning/error`
- `warning`：输出 `warning/error`
- `error`：只输出 `error`
- `silent`：文件和控制台都不输出

这样可以确保：

- 行为一致
- 配置简单
- 运行期调试时不需要维护两套级别配置

## 8. 配置设计

第一版采用轻量顶层配置字段，不新增独立 `log:` 配置块。

新增配置字段如下：

```yaml
log-level: info
log-file: /var/log/sdc-mihomo/mihomo.log
log-file-format: text
log-file-append: true
log-file-max-size: 20
log-file-max-backups: 5
log-file-max-age: 7
log-file-compress: true
```

字段定义：

- `log-file`
  日志文件路径，默认值为 `/var/log/sdc-mihomo/mihomo.log`。
- `log-file-format`
  第一版只支持 `text`。
- `log-file-append`
  是否以追加模式打开日志文件。
- `log-file-max-size`
  单个日志文件最大大小，单位 MB。
- `log-file-max-backups`
  保留旧文件数量。
- `log-file-max-age`
  旧文件最大保留天数。
- `log-file-compress`
  是否压缩旧文件。

说明：

- 默认日志文件路径为 `/var/log/sdc-mihomo/mihomo.log`
- 若用户显式将 `log-file` 设为空，则文件输出关闭
- 若启用文件输出，滚动参数使用上述配置
- `log-file-format` 在第一版仅接受 `text`

## 9. 文件 writer 设计

### 9.1 职责

文件 writer 负责：

- 打开目标文件
- 格式化日志行
- 串行写入
- 关闭文件
- 在配置变更时完成切换

### 9.2 抽象

在 `log` 包内部新增输出抽象，建议形式如下：

```go
type output interface {
	Write(Event) error
	Close() error
}
```

至少包含两类实现：

- console output
- file output

### 9.3 writer 生命周期

文件 writer 生命周期由 `log` 包统一管理：

1. 启动或配置加载时初始化
2. 配置 reload 时创建新 writer
3. 新 writer 可用后替换旧 writer
4. 关闭旧 writer

不允许业务模块自行持有文件句柄。

## 10. 滚动策略

第一版即内建滚动，并使用成熟库实现，不自行手写 rotate 逻辑。

滚动策略要求：

- 按大小滚动
- 支持旧文件保留数量限制
- 支持旧文件保留天数限制
- 支持压缩历史文件

这样设计的原因：

- 软件常驻运行，文件无限增长风险不可接受
- 自研滚动逻辑容易踩跨平台和边界条件问题
- 成熟库可显著降低实现风险

## 11. 配置应用与热更新

### 11.1 启动加载

配置解析后，在日志配置应用阶段初始化文件输出能力。

建议接入点：

- [config/config.go](/vm/project/github/clash-meta/mihomo/config/config.go:1)
- [hub/executor/executor.go](/vm/project/github/clash-meta/mihomo/hub/executor/executor.go:78)

### 11.2 reload 更新

配置热更新时支持以下行为：

- 开启文件输出
- 关闭文件输出
- 修改日志文件路径
- 修改滚动参数
- 修改 append 配置

更新流程固定为：

1. 基于新配置构造新 file writer
2. 构造成功后替换当前 writer
3. 关闭旧 writer

若新 writer 构造失败：

- 保持旧 writer 不变
- 输出内部错误告警
- 不影响当前日志主功能

## 12. 错误处理

文件日志是增强能力，不是主业务依赖，因此错误处理遵循以下原则：

### 12.1 不影响主业务

文件打开失败、写入失败、滚动失败都不能导致代理主进程退出。

### 12.2 不递归打日志

文件输出内部出错时，不能再调用 `log.Errorln` 之类的上层接口，否则可能形成递归。

内部错误应直接：

- 写 `stderr`，或
- 用底层 logger 打内部告警

### 12.3 限频告警

当磁盘满、权限错误、路径不可写等问题持续存在时，不应每条日志都重复输出同类错误。

要求：

- 对文件输出故障做限频告警
- 恢复后补一条恢复提示

## 13. 目录与路径策略

默认日志文件路径为 `/var/log/sdc-mihomo/mihomo.log`。

路径策略定为：

- 未配置 `log-file`：使用默认路径 `/var/log/sdc-mihomo/mihomo.log`
- 显式配置了 `log-file`：使用用户指定路径
- 显式将 `log-file` 设为空：不启用文件输出
- 父目录不存在时，可自动创建

跨平台要求：

- 不依赖 Linux 特有路径语义
- 兼容 Windows 文件句柄占用差异
- 兼容路由器/嵌入式场景的小磁盘环境

## 14. 与现有模块的关系

### 14.1 与 `stdout` 的关系

控制台输出保留，不因启用文件日志而关闭。

即默认行为是：

- 继续输出到 `stdout`
- 同时输出到文件

### 14.2 与 `/logs` 的关系

`/logs` 继续从 `logCh` 订阅实时日志事件，不从文件反向读取。

文件输出的引入不改变 `/logs` 接口协议，也不改变 UI 消费方式。

### 14.3 与 `log-level` 的关系

仍只维护一套 `log-level`。文件输出不单独增加自己的级别配置。

## 15. 测试要求

实现完成后至少覆盖以下测试场景：

1. 配置有效路径时，日志能正常写入文件
2. `log-file` 使用默认值时，能正常创建并写入文件输出
3. 路径非法或不可写时，程序不退出
4. `silent` 级别时，不写控制台也不写文件
5. 配置 reload 后切换到新文件路径
6. `log-file` 显式设为空后，关闭文件输出
7. 滚动阈值触发后，生成历史文件
8. 历史文件保留与压缩策略生效

## 16. 实施步骤

### 第一步：重构日志分发

修改 [log/log.go](/vm/project/github/clash-meta/mihomo/log/log.go:1)：

- 把当前 `print()` 重构为统一分发层
- 保留现有 `Event` 和 `Subscribe` 机制
- 为文件输出预留接入点

### 第二步：实现文件 output

- 新增文件 writer
- 实现文本格式输出
- 接入成熟滚动库
- 实现打开、写入、关闭

### 第三步：扩展配置

- 在配置结构中增加顶层日志文件字段
- 增加解析、默认值和合法性校验

### 第四步：接入配置应用与 reload

- 启动时初始化文件输出
- reload 时切换 writer

### 第五步：补测试

- 单元测试
- reload 行为测试
- 滚动行为测试

## 17. 最终结果

功能落地后，mihomo 的日志系统将变为：

`业务日志调用 -> Event -> 统一分发 -> stdout + rotating file -> /logs`

该设计在保持现有日志模型稳定的前提下，增加了可靠的本地日志持久化能力，并为后续继续扩展日志配置保留了空间。
